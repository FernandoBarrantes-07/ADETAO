## 1. Base de datos

Fuente de columnas: `supabase/migrations/20261009141945_remote_schema.sql`. Confirmación de RLS, políticas, trigger, índices y FK: `docs/db_schema.json`.

- [x] Tabla `public.clubes` — evidencia: `CREATE TABLE` en el baseline, líneas 76-88. Columnas: `id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL` (PK `clubes_pkey`), `nombre varchar(150) NOT NULL`, `ubicacion varchar(250)` nullable, `descripcion text` nullable, `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()`. El esquema de referencia de `AUDITORIA_PROYECTO.md` §4 dice `GENERATED ALWAYS`; el `db pull` dice `BY DEFAULT`. Se toma la migración. `db_schema.json` no trae la lista de columnas.
- [x] Nombre único — evidencia: `CONSTRAINT clubes_nombre_unique UNIQUE (nombre)` y el índice `clubes_nombre_unique` (`db_schema.json`, `clubes_nombre_unique`). El único de `varchar` distingue mayúsculas: "Club Norte" y "club norte" son dos filas.
- [x] Estado `activo` / `inactivo` — evidencia: `ALTER TABLE public.clubes ADD COLUMN estado public.record_status NOT NULL DEFAULT 'activo'` en el baseline. El enum `record_status` vale `activo`, `inactivo` (`db_schema.json`, enums). Es el enum compartido con arqueros, categorías, perfiles y tipos de arco.
- [x] `updated_at` automático — evidencia: trigger `trg_clubes_updated_at` BEFORE UPDATE, función `actualizar_updated_at()` (`new.updated_at = now()`). El mismo trigger está en `db_schema.json`.
- [x] Relación con arqueros — evidencia: `arqueros.club_id bigint` nullable y `arqueros_club_id_fkey`: `FOREIGN KEY (club_id) REFERENCES clubes(id) ON UPDATE CASCADE ON DELETE SET NULL` (baseline y `db_schema.json`). Borrar un club deja `club_id` en nulo y no impide el borrado. Índice `idx_arqueros_club` sobre `arqueros(club_id)`.

## 2. Permisos (RLS)

RLS activo en `clubes` (`ALTER TABLE public.clubes ENABLE ROW LEVEL SECURITY` y `db_schema.json`, `"tabla": "clubes", "rls_activo": true`). Las políticas están solo para `authenticated` y no consultan `perfiles.rol`. `es_admin()` y `es_staff()` no aparecen en ninguna política de `clubes`.

| Rol | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| administrador | sí, `USING (true)` | sí, `WITH CHECK (true)` | sí, `USING` y `WITH CHECK (true)` | sin política: la API lo niega |
| profesor | igual que administrador | igual | igual | igual |
| usuario | igual que administrador | igual | igual | igual |
| anon | GRANT sí; sin política, RLS lo niega | igual | igual | GRANT sí; sin política, RLS lo niega |

- [x] Tres políticas de lectura y escritura para cualquier autenticado — evidencia, baseline y `db_schema.json`: `Usuarios autenticados pueden consultar clubes` (SELECT, `qual: true`), `Usuarios autenticados pueden insertar clubes` (INSERT, `with_check: true`), `Usuarios autenticados pueden actualizar clubes` (UPDATE, `qual` y `with_check: true`).
- [~] El permiso no distingue rol — administrador, profesor y usuario pueden consultar, insertar y actualizar cualquier club. El menú de `Sidebar.jsx` oculta Clubes a quien no es administrador; la BD no. Falta usar `es_admin()` como en `tipos_arco`.
- [x] Un autenticado no puede borrar un club por la API — evidencia: no existe política DELETE sobre `clubes` (el baseline y `db_schema.json` solo listan SELECT, INSERT y UPDATE). Con RLS activo, la ausencia de política niega el DELETE. El GRANT de la tabla sí incluye DELETE.
- [~] Grants amplios, incluido `anon` — evidencia: el baseline hace `GRANT DELETE, INSERT, MAINTAIN, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE ON TABLE public.clubes TO anon, authenticated`, y `GRANT SELECT, UPDATE, USAGE` sobre `clubes_id_seq` a `anon` y a `authenticated`. `anon` no tiene política, así que RLS lo niega mientras el RLS siga activo. - [ ] Políticas por rol y `REVOKE` a `anon` — patrón a seguir: `tipos_arco` en `20261009150500_inventario_rls.sql` (SELECT para `authenticated`; INSERT y UPDATE con `es_admin()`) y el `DROP POLICY` de DELETE de `tipos_arco` en `20261010120000_inventario_reglas_prestamo.sql`.
